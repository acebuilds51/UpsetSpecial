## Changes

### 1. keepWarm no longer rebuilds the whole state every 5 minutes
- **What was wrong:** every keepWarm run re-read 8+ sheets (Players incl. avatars, Season, Rotation, Games, Bowl×3, LineSnapshot, NameClaims, CareerHistory), even overnight when nothing had changed. Each run also took more than 4s, so each one appended a "slow" PerfLog row, adding another sheet write.
- **Evidence:** ~7s average × 288 runs/day ≈ 34 min/day of the ~90 min/day trigger quota.
- **What changed:**
  - keepWarm reads the cached state first and uses it for the live-games check. Before, `maybeAutoFetchScores_(null)` re-read the Season and Games sheets.
  - keepWarm rebuilds only if: scores were just fetched, the cache is missing or was busted by a write, or the build is older than 15 min (a safety net).
  - New installable `onSheetChange` trigger (`installSheetChangeTrigger()`, run once). Any manual sheet edit (typing, pasting, inserting or deleting rows) now busts the state and career caches immediately. Today such edits take up to 5 min to show.
  - **Safe until installed:** keepWarm only skips rebuilds while Script Property `sheetChangeTrigger` = `1`. `runDiagnostics` resyncs that flag nightly with the real trigger list. Without the trigger, behaviour is exactly what it is today (rebuild every run).
  - The trigger-run snapshot jobs (`weeklyMondaySnapshot`, and `autoBackfillMissingLines` when it adds rows) now bust the cache themselves, because `snapshotCount` is cached.
  - When watched, the state cache TTL is 25 min (1500s), longer than the 15-min max age plus one keepWarm interval.
- **Expected impact:** outside live-game windows, most runs become a cache read plus two property reads, well under 1s, down from ~7s. Rough estimate: 34 → ~8 min/day of trigger runtime. keepWarm should also mostly drop out of PerfLog's "slow" rows.
- **Tests:** unwatched keepWarm still rebuilds every run. Watched keepWarm skips when fresh, and rebuilds after an app write, after `onSheetChange`, and after 15 min. Live-game keepWarm caches fresh scores. Diagnostics clears the flag when the trigger is gone. The missing-lines job refreshes `snapshotCount`.

### 2. CareerHistory cache actually stays warm
- **What was wrong:** the cache TTL was 300s, the same as the keepWarm interval, so the cache had usually just expired whenever keepWarm or a user arrived. It was also a single key capped at 90KB, so it silently stopped caching once the sheet grew past that. It feeds `memberSince` on every state rebuild, the leaderboard, career history, and the Trophy Room.
- **What changed:** the cache is now chunked (`careerHistory_v2`, same helpers as the state cache). TTL is 6h when `onSheetChange` is installed, 6 min otherwise. `invalidateCareerHistoryCache()` now also busts the state cache, since `memberSince` comes from CareerHistory.
- **Bug fixed along the way:** `adminFixCareerMapping` never invalidated the career cache, and it wrote one row per `setValues` in a loop. It now groups consecutive rows into one write and busts both caches. Same rows and values as before.
- **Expected impact:** less keepWarm time, and a faster getTrophyRoom and leaderboard on a warm cache. The Trophy Room still reads ~9 other sheets; see "not done".
- **Test:** cached read hit, fix-mapping updates exactly the matching rows, and `memberSince` refreshes.

### 3. getState payload trimmed (no frontend change)
- **What was wrong:** every app open and 90-second poll re-downloads every pick of the season, each carrying `_row` (server-only row number, never read by the app) and a full ISO `submittedAt`.
- **What changed:** `_row` is stripped from every array in getState. `submittedAt` is dropped for picks from weeks **before last week**. The app reads `submittedAt` in one place only: the player's own draft-sync fingerprint for the week being picked (`renderPicksBoard`). It's kept for the current and previous week in case the admin advances the week while a game is still open. All other fields are unchanged.
- **Evidence:** a typical pick is 182 → 129 bytes (−29%) for past weeks and 182 → 170 bytes for recent weeks.
- **Expected impact:** roughly 15–25% smaller getState now (≈517KB → ~400KB), growing to ~25% late in the season. This is not the full fix for priority (b); see "not done".
- **Test:** no `_row` anywhere in the response. Last week keeps `submittedAt`, older weeks lose only that field, and standings are still OK.

### 4. Diagnostics summary could never be read on a busy week
- **What was wrong:** `saveDiagnosticsSummary_` stored `JSON.stringify(summary).slice(0, 8500)`. Whenever the report was bigger than that (many warnings or PerfLog actions, which is when it's needed), the stored text was invalid JSON. `getDiagnosticsSummary` then returned `summary: null`.
- **What changed:** the summary is shrunk until it fits: clip long error strings, then drop the lowest-ranked perf rows and warnings, and mark it `truncated: true`. It works on a deep copy, so the emailed report is untouched.
- **Test:** a huge report still round-trips as valid JSON, stays ≤ 8500 chars, and leaves the original report unmodified.

### 5. Small correctness fix
`deleteRowsByMatchFast_` didn't clear the request-scoped sheet cache, so a later read in the same execution could still see the deleted rows. Current callers happened to clear it manually. It now invalidates itself.
